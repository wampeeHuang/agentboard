# 中间态不能折叠成失败：巡检轮次与任务终态要分开建模

## 现象

- Inspector 在一次全量巡检中报“快照缺失或过期”，但同一轮后续检查很快写入并通过。
- Scheduler 的文件产出任务仍在执行，`outputCheck.ok` 为 `null`，总览却显示 `output_missing`。
- 用户看到的是多个红色异常，实际业务任务已在正常运行或会在本轮结束后通过。

## 根因

系统只按布尔结果聚合，丢失了两个中间态：

1. **巡检轮次未封存**：依赖全局快照的检查与普通检查混在同一执行序列。快照尚未生成时，检查器把“尚未写入”解释成“缺失”。
2. **任务尚未终态**：`outputCheck.ok=null` 的语义是“运行中或尚未验收”，却被与 `false` 一样处理为失败。

这会把时间上的先后关系伪装成业务故障，告警因此失去可信度。

## 修复模式

### 巡检：两阶段提交

1. 执行并追加所有普通检查结果。
2. 从完整日志投影快照。
3. 执行声明为 `phase: "finalizer"` 的缓存、汇总和全局不变量检查。
4. 再投影一次快照，发布最终结果。

`finalizer` 不得检查自身是否已经出现在当前缓存中；它只验证常规检查的完整性。

### 任务：终态后验收

文件产出应至少区分三态：

| 状态 | `outputCheck.ok` | 告警语义 |
| --- | --- | --- |
| 运行中 | `null` | 待终态验收，不报产出缺失 |
| 成功终态 | `true` | 通过 |
| 失败或结束未验证 | `false` / 缺失 | 报产出异常 |

运行中状态必须有截止条件：超过任务声明的超时窗口和宽限期后，仍未达到终态的记录应显式失败，避免用“pending”掩盖卡死。

## 验证清单

- 构造运行中的文件任务：巡检应通过且输出“待终态验收”。
- 构造结束但文件校验失败的任务：巡检必须失败。
- 构造超时未结束的任务：巡检必须失败。
- 运行全量巡检：finalizer 只能在快照完整后执行，面板不得出现本轮中途的“未检查”误报。

## 预防

- 在状态机设计时，把 `pending`、`success`、`failed`、`stale` 作为不同状态，不把未知或进行中映射为布尔失败。
- 将跨项目、读缓存、读汇总的规则明确标成收尾阶段，并在执行器中统一排序；不要依赖 JSON 声明中的偶然顺序。
- 告警只对终态失败或超时未终态发送；面板可展示 pending，但不能以异常计数放大它。
