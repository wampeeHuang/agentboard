# 往追加型文档写内容：读全文 → 头部插入 → 整体写回，不能只写新内容

## 现象

会话收尾要往 `D:\Obsidian\HANDOFF.md` 追加本次交接。按"新段置顶"的既有惯例，直接调 `write` 把新段落作为**整文件内容**写进去。

结果：文件从原来的 **97 行缩到 87 行**，后面两节（2026-09-13、2026-08-25）被截断。

更糟的是补救路径全断：`HANDOFF.md` 在 `.gitignore` 里（注释写明「per-session state, not project content」），`git ls-files` 为空 → **无 git 历史**；回收站里也没有（是覆写不是删除）。唯一恢复来源是**本会话上下文里早前那次完整读取**。

## 根因

两个认知叠在一起：

1. **把 `write` 当成了"追加"语义。** 它是**整文件替换**——工具描述里写了「Existing files are overwritten」，但"新段置顶"的惯例让人下意识只准备新内容。
2. **忽略了这类文件的特殊性**：HANDOFF / log / 台账是**只增不减**的累积文档，其价值全在历史累积。对它们做整文件替换，等于用最新一页盖掉整本书。

同类文件：`log.md`（追加式操作日志）、各类 `HANDOFF`、`ledger` / `台账` / `CHANGELOG`。

## 修复/步骤

1. **先读全文**（`read` 拿到完整内容，不留 offset/limit）。
2. **在内存里拼接**：新段 + 原全文。
3. **整体写回**。
4. 写回后**核对行数**：新文件行数 ≈ 原行数 + 新增行数。**行数变少就是截断了**，立刻停下。

对 `log.md` 这类"末尾追加"的，用 `edit` 命中最后一行做替换追加更安全（不涉及整文件重写）。

## 预防

- **区分"覆盖型文档"与"累积型文档"**：前者（报告、笔记正文）可以整文件重写；后者（HANDOFF / log / 台账 / CHANGELOG）**永远不要整文件写**。
- 动累积型文档前先问一句：**这个文件有版本控制兜底吗？** 本例 `.gitignore` 明确排除了它 —— 没有兜底时，一次误写就是永久损失。
- **`.gitignore` 里排除的"会话态"文件最容易出事**：它们看起来像普通 Markdown，但既没历史、又常是长文档，且往往只被 append。
- 覆写后立刻做一次**体量自检**（行数/字节数对比），把它当成交付前的固定动作。
- 恢复靠上下文时，**明确标出无法还原的缺口**，不要为了让文件"看起来完整"而补写推测内容。
