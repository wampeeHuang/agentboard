# 无基线的首轮同步会把云端旧布局拉回本地，判据是"目录新、文件旧"

## 现象

修好授权后首轮同步报告成功（`succeeded 1951`），但本地 vault 的 `wiki/` 从 378 个文件涨到 1054 个：
多出 `wiki/prompts/`、`wiki/references/`、`wiki/scripts/`、`wiki/CLAUDE.md`、`wiki/_runtime/`、`wiki/理解/`
等**根目录同名副本**，内容全是 7 周前（8/14-8/15）的旧版。git 显示 681 个新的未跟踪文件，
其中 635 个是 `wiki/实体/网站/*.md`。

## 根因

该 vault 在 8 月时的目录布局与现在不同（prompts / references / scripts 当时在 `wiki/` 下，`理解/` 尚未移出），
云端镜像停在 8/15。插件本地**没有同步基线**（`.airsync/metadata.json` 不存在），
于是把"远端有、本地无"的路径一律当成新增 → 下载回本地。
协议上没错（首同步保守合并、只补不删），但方向与用户预期相反：用户要的是"本地 → 云端"。

## 判据（一眼认定"这是刚拉回来的"而非"本地原有"）

同步类工具下载时会**保留远端 mtime**，但**目录是本轮才创建的**：

```bash
stat -c '%y %n' wiki/prompts          # → 本轮时间（目录刚建）
stat -c '%y %n' wiki/prompts/x.md     # → 8 月旧时间（文件是下载的）
find wiki -type f ! -newermt "2026-08-16" | wc -l   # 旧时间戳文件的规模
git status --porcelain -uall | grep -c '^??'        # 新出现的未跟踪文件
```

**反向验证同样重要**：`git status` 里"已修改"的被跟踪文件若 mtime 都是近两周的正常时间，
说明**内容没被覆盖**；只有 mtime 落到旧日期的才是被远端盖掉的。
本次 40 个已修改文件全是 9/20-10/2 的正常改动，唯一被覆盖的只有 3 个 `.obsidian` 配置文件。

## 修复/步骤

1. **先停插件**，别让它继续跑
2. 清理：删"未跟踪 **且** mtime ≤ 旧镜像日期"的集合（本例 681 个）——**不要用"未跟踪"单独做判据**
3. **重置云端**：清空云端镜像文件夹（不要删除文件夹本身，否则绑定的 folder id 会失效），
   或换一个空文件夹重新绑定 → 让它变成"远端空 → 只推不拉"
4. 重跑，确认 plan 里 `pull = 0`

## 预防

- 换同步工具、或同步停摆数周后重启，**先确认云端镜像与本地是否同源**，别直接跑首同步
- 判断方向是否安全，看 plan 的 `push/pull` 计数：`pull` 大＝它在往本地灌
- 首同步前能拿到云端清单的话，先比顶层目录名
