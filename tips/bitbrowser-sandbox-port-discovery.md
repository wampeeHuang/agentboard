# 比特浏览器沙箱的 CDP 端口无法靠"扫监听端口"发现，要用沙箱内工作台页反查

## 现象

矩阵账号面板（:15502）显示「没有发现已登录的账号窗口」，但比特浏览器里明明开了 4 个平台的登录页（B站/小红书/抖音/公众号）。

面板同时报 CDP 端口发现为空，或把端口判成「不是比特沙箱」。

## 根因

旧发现逻辑是：`netstat` 列出所有监听端口 → 逐个请求 `http://127.0.0.1:<port>/json` → 从返回页面里找平台域名。

对比特浏览器这个思路必然失效，有两层原因：

1. **端口号推不出来**。比特启动沙箱用的是 `--remote-debugging-port=0`，
   由系统随机分配端口，**端口号不落在进程命令行里**，也不在沙箱配置里。
   命令行里只能看到 `--user-data-dir=...\BrowserCache\<沙箱id>`。
   所以按进程参数解析也拿不到端口。

2. **沙箱里混着非目标页面**。每个沙箱都会自动开一个工作台页
   `https://console.bitbrowser.net/?id=<沙箱id>&locale=zh&port=54921`，
   如果面板自己也开在这个沙箱里，还有面板页面。
   按"页面里有没有平台域名"来判断，会把工作台页和面板页一起搅进来。

实测对照：真实沙箱端口是 64048，旧逻辑把它判为「不是比特沙箱」；
它在别处扫到的 9222 其实是 Docker 的调试端口。

## 修复/步骤

改成**确定性锚点反查**，三步：

1. **沙箱列表读 API**（权威源，带平台/账号/运行状态配置）：
   ```
   POST http://localhost:54921/browser/list   {"page":0,"pageSize":200}
   ```
2. **端口用工作台页反查**：枚举候选监听端口，对每个端口取 `/json/list`，
   在页面 URL 里正则匹配 `console\.bitbrowser\.net/\?id=([0-9a-f]{32})`，
   命中的沙箱 id 就是该端口所属沙箱。零猜测、零误报。
3. **登录态用 cookie 实测**（只读）：连该端口标签页的 `webSocketDebuggerUrl`，
   `Network.enable` → `Network.getCookies({urls:["https://<平台域名>"]})`，
   看登录 cookie 名是否存在：
   B站 `SESSDATA`/`DedeUserID`、小红书 `web_session`、
   抖音 `sessionid`/`sessionid_ss`、公众号 `slave_sid`/`bizuin`。

验证：面板页面实测渲染出 3 沙箱、运行中 1 个、4 个平台全部「已登录」，各带命中依据。

## 预防

- **不要用"猜端口 + 试探"来发现随机端口的服务**。有配置源就读配置源；
  没有就想办法找一个**由该服务自己产生的确定性锚点**（这里是它自己开的工作台页 URL）。
- 判断"某端口属于哪个进程"时，除了命令行，还可以看**该进程自己打开了什么页面**——
  页面 URL 里的 id 参数往往比命令行更可靠。
- 比特 API `:54921` 只监听 IPv6 `::`，必须用 `localhost`，用 `127.0.0.1` 连不上。
- 沙箱未运行时扫不到任何平台——这是预期行为，不是故障。
