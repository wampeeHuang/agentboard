# 零备份的外部产出：一次性脚本 ≠ 固定动作；而 git 的行尾转换会让"字节保真"的备份变形

## 现象

项目里发现某份产出（示例：`D:\Obsidian\inbox\*.canvas`）**不在任何备份里**——不在本仓库、不在其自身
vault 的 git（那个仓库 `.gitignore` 明确排除 `inbox/`）、也不在异地镜像。第一轮"补"的办法是**手写一次性脚本**：
日期写死、落在既不进 git 也不进镜像的 `_runtime/`、无条件全量复制、没有门禁。
**结果第二轮又得重写一遍**：洞还是那个洞，动作每次重来。

同一轮里还查出一件事：本仓库 `core.autocrlf=true` 且无 `.gitattributes`，于是

| | 字节 | CRLF | sha256 前 16 |
| --- | --- | --- | --- |
| 原工作区 | 14255 | 0 | `acae8625f46288b3` |
| `git clone` 出来 | **14370** | **115** | `a6c4a8cbba3c08be` |

JSON 内容没坏，但**这份快照的唯一价值就是字节保真、判据就是哈希**——哈希跨机器全变，
换台机器恢复后门禁把"其实没变"报成"内容已变"。

## 根因

1. **把"诊断"当成"机制"。** 诊断产出一次性动作（"已经复制过去了"）；机制要能重复执行、能被判成败、
   能被人以外的东西执行。自检问题：*换个不知道上下文的会话来，他能不能只靠仓库把这件事再做一遍？*
2. **判据问错了问题。** 该问"**东西存住了没有**"（可对内容哈希回答），而不是"脚本今天跑过没有"（靠记忆，且答不了正确性）。
3. **默认"进了 git 就等于字节还在"。** git 存的是规范化后的内容、取出时按平台转回。
   会悄悄动字节的载体还有：文本编解码、云盘同步、富文本编辑器。

## 修复/步骤

1. 固定动作落成**仓库内**的脚本（进 git + 进镜像），口径写进 docstring：
   比内容哈希不比 mtime（编辑器会重写文件）、幂等（内容没变就 0 复制）、只增不删、
   **同日重跑覆盖前记 from→to 哈希**（否则唯一好副本被无声覆盖）、
   坏件不入档但好文件照存且**退出码非 0**。
2. 一条机器门禁 `--check`：问"现有快照是否完整覆盖当前源"，退出码分级（已覆盖/未覆盖/源不可用/有坏件）。
   ⚠ 扫目录要用 `**/`：快照落在 `archive/YYYY-MM/` 里，写成 `*/` 会**永远扫不到**（门禁恒红或恒绿）。
3. 机制测试隔离临时根；**"真实状态是否已备份"不进 pytest**（用户白天改文件会让测试常年报红，红灯一多就没人看）。
4. 保字节的产物加 `.gitattributes`（如 `*.canvas -text`），并**用 `git clone` 到临时目录逐字节复验**。
5. 写进项目契约的收尾口径（"收尾第一件事就是跑它，跑完 --check 复核"），不只写在交接文件里。

## 预防

- 观察到"某产物零备份"，交付物必须是**"能重复跑的脚本 + 能被机器判的判据"**，不是一次性的复制动作。
- 判据问结果、不问过程。
- **拿哈希当判据前，先证明载体保字节**（一次 clone + 逐字节对比，一分钟）。
- 别把"已经补过一次"当成"以后不用再管"：补的是动作还是机制，看有没有留下能复跑的东西。
- 相关：`artifact-tier-by-regenerability`（按能否再造分层）、`knowledge-assets-gitignore-no-version-history`
  （被 gitignore 的知识资产无版本保护）、`edit-tool-crlf-match-failure`（autocrlf 影响编辑工具匹配）。
