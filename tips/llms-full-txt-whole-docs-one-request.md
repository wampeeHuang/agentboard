# 官方文档站的 llms-full.txt 是整站原文出口，调研第一件事就查它

## 现象

要拆一个产品（Descript）的产品结构与功能全貌，按常规做法是逐页抓帮助中心、逐篇清洗 HTML。这条路的成本随文档量线性增长：该站 26 个板块 399 篇文档，逐页抓要发 399 次请求、每次都要剥离导航与脚本。

实际只发了 **1 次请求**：`https://help.descript.com/llms-full.txt` 返回 **1.22 MB 纯 Markdown，含全部 399 篇的正文**，每篇以 `# 标题` + `Source: <URL>` 开头，正文是官方自己产出的 Markdown（带链接、表格、callout 语法）。另有 `llms.txt` 给全站文档目录（407 条链接）。

## 根因

`llms-full.txt` 是 llms.txt 规范的**全文变体**：`llms.txt` 只给页面清单，`llms-full.txt` 把所有页面正文拼在一个文件里，供 LLM 一次性读入。文档托管服务（该站用 Mintlify）会自动生成这两个出口，站点方通常无需额外维护。

已有一条 tip `llms-txt-ai-crawler-directory.md` 讲的是**站方视角**（自己建站该发布 llms.txt）。本条是**调研方视角**：去抓别人时，先看有没有这个出口。

## 修复/步骤

1. 抓任何文档站之前，先探测这几个路径（成本极低，各 1 次请求）：
   - `/llms.txt` — 页面清单
   - `/llms-full.txt` — **全文**（本条的宝藏）
   - `/llms-full.md`、`/.well-known/llms.txt` — 部分实现用这些变体
2. 拿到全文后按 `\n(?=# )` 切分成单篇，用 `Source:` 行还原每篇的原始 URL —— 于是「一次抓取」得到的仍是**逐篇独立、可审计**的原文，不牺牲来源链。
3. 逐篇落盘时保留英文 H1 与 `> 原始来源：URL` 标记，正文再按知识库要求加工（如译成中文），审计线索不丢。
4. 单页也有纯文本出口：任意文档页路径后加 `.md`（该站实测可用），适合只补某一篇。

## 预防

- 调研取证的**第一步**是探测机器可读出口，不是开始抓 HTML。这一步漏了，后面所有清洗工作都是白做的。
- 判断依据不是"有没有 llms.txt"这一个文件，而是**文档托管平台**：Mintlify / 多数现代文档站默认生成全文出口。
- 全文出口拿到的链接结构比 HTML 抓取更完整（表格、内部链接、callout 都保留），后续做信息架构统计（板块数、篇数）可以直接数，不必再猜。
