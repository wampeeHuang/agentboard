# 门禁"每文件只报第一条"：改完必须用同一条正则全量复扫

## 现象
vault 的 `check.js` 报 **4 项违规**（中文粗体后必须接冒号）。按它给的位置改完再跑，又报出**新的 2 条**；
改完再跑又报 2 条 —— 三轮才见底。
读它的实现才发现：那条正则做的是 `withoutCode.match(/\*\*([^*\n]{1,20})\*\*([。，])/u)` ——
**非 global，每个文件只返回第一个匹配**，所以"报 4 条"的真实含义是"4 个文件各至少有一条"。
用同一条正则（global）本地全量扫，两个文件里实际有 **13 处**。

## 根因
门禁为**可读性**只打印首个匹配（避免一次刷屏），而使用者把"报了几条"当成"总共有几处"。
两者在有多个同类问题时会差一个数量级；更糟的是它表现为"改一条、又冒一条"的挤牙膏循环，
很容易被误判成"规则还在变"或"工具在乱报"。

## 修复/步骤
1. 打开门禁实现，把它的正则/判据**原样抄出来**（不要自己重写一条"差不多的"）。
2. 本地按该正则 **global 全量扫**，列出每一处（文件 + 行号 + 命中片段）。
3. 一次性全改，再**用同一条正则复扫**，要求"残留 = 0"才算收工。
4. 把"全量扫 + 复扫"做成脚本（下次直接跑），并在脚本注释里写明判据来自哪个文件的哪一行。

## 预防
- 看到门禁报"N 条"，先确认它是不是**每文件首匹配**；是的话，N 只是"涉及文件数"。
- 修任何"格式类"门禁，收工判据都是**同正则残留 0**，而不是"再跑一次不报了"（后者可能只是换了下一个匹配）。
- 同理适用于 lint/编译器的"首错即停"：改一条再跑，等于用 N 轮换 1 轮，成本高且容易漏。
