# 多服务工具启动：不写文档，写自愈脚本

## 为什么文档不够

工具启动失败时，人的第一反应不是读 README，是反复点按钮。Agent 的第一反应是逐层查端口、查进程、查日志——每次从头推理，慢且漏。

**核心洞察：启动失败的原因是已知的、有限的、可程序检测的。不需要每次重新推理。**

## 模式：Pre-flight → Auto-fix → Start → Verify

把启动命令从"盲目跑批处理"改成"带自愈的脚本"：

```
Phase 1 — Pre-flight（程序检测，不是人判断）
  ├─ 自有端口冲突 → 自动杀（安全：这些端口只有自己能占）
  ├─ 外部端口冲突 → 警告 + 交互选项 [继续/放弃/帮你杀]
  └─ 路径/依赖 → 阻断 + 报具体缺失

Phase 2 — 启动（在干净环境中启动所有层级）

Phase 3 — 验证（启动后确认端口全在线，不是"跑完没报错就算成功"）
```

## 安全边界

| 操作 | 策略 | 原因 |
|------|------|------|
| 杀自己端口的残留进程 | **自动** | 8001/3001/5173 只有 ACE Step 用，残留 = 上次没清干净 |
| 杀其他工具的进程 | **交互确认** | ComfyUI/MiniCPM-V 用户可能正在用 |
| 路径/依赖缺失 | **阻断 + 报错** | 修不了，必须人来 |

## ACE Step 实现参考

- `D:\tools\ace-step\start.ps1` — 自愈启动脚本
- `D:\tools\ace-step\diagnose.ps1` — 纯诊断（不修，只报）
- 工具架 manifest `startCommand` 指向 `start.ps1`

## 适用场景

任何满足以下条件的工具都应该用这个模式：
1. 多进程/多服务架构（≥2 层）
2. 已知的失败模式有限（端口冲突、依赖缺失、资源不足）
3. 启动按钮预期由人点击（不是 cron 自动化）
