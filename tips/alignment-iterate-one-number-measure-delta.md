# 对齐类修改要"先量差值再改一个数"，并且先分清量的是字还是框

## 现象

用户连续 5 次指出"没对齐"（「对齐！！」「还是没有在领域和结构化描述这两个地方实现对齐呀」）。
每次我都"改了但没对齐"，而且每次都以为自己量对了。

## 根因（四个不同的错，看起来一样）

1. **量错对象**：用户说"对齐视觉事实"，我改的是**组名**；他要的是**判断项名**那条线 ——
   两个元素都叫"名字"（`.struct-axis__name` / `.struct-row__name`），我拿错了。
2. **量错层**：`getBoundingClientRect().left` 是**盒**左缘，而对齐看的是**字**左缘，
   两者差 = `border-left + padding-left`（实测 9px）。我把"盒对盒"写成断言 →
   **断言在 649 处恒真**，一直绿、画面一直错。
3. **量错值**：探针没固定 `scrollY`，同一份样式量出不同 y，报出 **109 处假变化**（全是 y 差 48）。
   假红比漏判更贵：会让人去改本来对的代码。
4. **改错范围**：共用选择器（`.tax-tree__children > li`）一动，**两个 tab 一起动**，只补一边就出现新错位。

## 修复/步骤

1. **一条断言只钉一个数，且钉"目标"而不是"结果"**。
   目标 = 用户点名的那条线（本例 640）；结果 = 盒子位置（会随别的改动漂）。
   钉结果等于把"当前实现"当契约。
2. **写一个"算差值"的探针**：读当前值 + 目标值 → 输出"CSS 该改成多少"，
   例：`判断项名的字 618 → 要 640：行 margin-left 现在是 -14px，改成 8px`。
   **按差值改一次再复量**，不要来回试 −9 → −10 → 8。
3. **input 没有文本节点**：`Range.getClientRects()` 量不出它的字 →
   字形左缘只能算：`框左缘 + borderLeftWidth + paddingLeft`（本项目踩了三次）。
4. **断言里写清"量什么、跟谁比"**：是盒还是字形、是同一层还是父子层。
   本项目既吃过分"内容盒 vs 盒"的假失败，也吃过分"盒对盒"的假通过。
5. **动共用 CSS 后跑指纹**：用另一个页面的 computed style 指纹
   （本项目 68 节点 × 47 条属性 + 盒子 + hover/focus）**证明**它零变化 ——
   "源码没动"不等于"生效结果没变"。
6. **量之前固定滚动位置**并把 `scrollY` 记进快照，y 变化时能立刻分辨是布局变了还是滚动不同。

## 预防

> 用户说"没对齐"时先答三问再动手：① **哪条线**（哪个元素、哪个 tab）？
> ② **量字的边缘还是框的边缘**？③ **跟谁比**（同一层吗）？答不清就先量、别改。
