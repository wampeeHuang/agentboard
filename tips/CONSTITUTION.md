# 操作日志宪法 · 工具架

> 一条经验日志「值不值得写、怎么写、写什么、怎么养」的唯一裁决。
> 本宪法以工具架（`~/.agentboard/tips/`）为单位。

---

## 〇、使用流程（先读这节）

**写入时**，按序走完五步，任何一步不过就停：

```
1. 准入 → 五问全过才落盘（capability 用放宽三条件）
2. 分类 → 这条日志回答什么问题（五类互斥）
3. 套模板 → 按类型填正文结构
4. 查不写入 → 别写进不该进的东西（本项目清单见 §四）
5. 落盘 → frontmatter + # 标题 + 正文；文件名 kebab-case；经 /api/tips 写入
```

**维护时**，四规则循环：过期即归档 · 发现即修 · 重复即合并 · 不凑数。

---

## 一、准入标准（五问）

写入前逐条过。五条全过才落盘，一条不过就放弃。

- **可复用吗** — 能帮助未来解决同类调度问题
  - 不通过示例：「6月12日重启了3次服务器」——一次性记录
- **非显然吗** — 合格开发者从代码/文档推断不出
  - 不通过示例：「Express 用 app.get() 注册路由」——查文档就有
- **学习成本高吗** — 踩这个坑花了 30 分钟以上才定位
  - 不通过示例：「少了个分号」——一眼就能看到
- **跨会话有价值吗** — 换一个任务、换一个 Agent，仍然有用
  - 不通过示例：「用户喜欢蓝色」——个人偏好
- **可操作吗** — 给出了下次怎么做不同的具体指令
  - 不通过示例：「localStorage 很坑」——模糊，没有行动指引

### 优先级速判

```
花了 1h+ 才定位的 bug → 必写
同一模式踩过 ≥2 次 → 必写
违反直觉的反转（API 200 ≠ 页面正常）→ 必写
看了代码就能知道的 → 不写
纯操作日志 → 不写
```

### capability 放宽准入

capability 不回答"为什么坏了"，门槛比五问低——不需要"踩坑花 1h+"，只需三条：

- **跨项目可复用** — 换一个任务/场景仍然能用
- **非显然** — 合格开发者不会立刻想到这个组合可行
- **有排他性** — 其他方式做不到或已被验证不可行

## 二、分类（五类）

同一维度：**这条日志回答什么问题**。一条日志只归一类。

- `diagnosis` **诊断** — 回答「为什么X会这样？」
  - 判定：因果链（现象→根因）
  - 示例：gh超时但git正常 → 因为gh不走git proxy
- `method` **方法** — 回答「怎么做X？」
  - 判定：可执行的步骤序列
  - 示例：备份顺序：.claude.json → tools/ → skills/
- `fact` **事实** — 回答「X在哪/是什么？」
  - 判定：具体数据：路径、版本、架构
  - 示例：工具注册在 ~/.agentboard/tools/ 下
- `capability` **能力** — 回答「我能用X在Y场景做什么？」
  - 判定：工具+场景=能力，防止"有这个能力但忘了用"
  - 示例：Chrome DevTools 能操控百度地图测通勤
- `feedback` **反馈** — 回答「用户/环境给我的行为纠正是什么？」
  - 判定：记录被纠正的做法 + 为什么
  - 示例：用户说"别 mock 数据库" → 集成测试连真库

互斥检验：一条日志不可能同时主要回答"为什么"又主要回答"怎么做"——诉求不同，写出来重点不同。

> **type 是"形式轴"，与"领域轴/作者轴"正交**（见 §三·领域与作者）。一条日志同时具有三个属性：type（回答什么问题）× domain（在哪个世界适用）× author（谁写的）。

## 三、格式

### 文件结构

YAML frontmatter（`---` 包裹）在前，正文 H1 标题在后。frontmatter 只放元数据，不放标题。

```markdown
---
type: diagnosis | method | fact | capability | feedback
domain: general | dsh | cron        # 必填，缺省 general
author: 人工 | dsh-agent | claude | codex | cron | 其他   # 必填，缺省 其他
date: YYYY-MM-DD
source: 触发写入的事件/任务简述
---

# 一句话标题（洞察，不是主题）

## 现象
（你看到了什么）

## 根因
（为什么发生——diagnosis必填，method/fact可省略）

## 修复/步骤
（怎么修好的 / 怎么做）

## 预防
（下次怎么避免）
```

### capability 专用格式

capability 只回答"我能做什么"，不需要现象/根因/修复。frontmatter 可扩展 `tool`/`scenario`/`recipe`：

```markdown
---
type: capability
tool: 工具名
scenario: 什么场景下用
date: YYYY-MM-DD
recipe: 详细操作手册的绝对路径（可选）
---

# 一句话标题（能力描述，不是工具名）

## 能力
（这个工具+场景组合能做什么事）

## 为什么只能用这个
（其他方案为什么不行——防止重复探索的关键）

## 速查
（一行命令或关键步骤，快速回忆怎么调）
```

### 格式约束

- type 必填，合法值由 `lib/tip-schema.js` 校验，不合规在 `/tips` 页面标红
- 一个文件一个洞察。不要合集
- 100 行以内。超过说明拆得不够细
- 中文为主，代码/变量名英文
- 文件名 kebab-case，语义化
- frontmatter 后空行再接 `# 标题`

## 三·补、领域与作者（独立口机制）

**domain 与 type 正交**：type 答"这是什么类型的知识"（形式轴），domain 答"这条知识在哪个世界适用"（领域轴）。二者相乘，同一个 domain 内可展开全部 5 类 type。

**domain 归属判据（依附性测试）**：
> **去掉某个系统，这条经验还成立吗？**
> - 还成立 → 不依附该系统，归 `general`（或它真正依附的系统）
> - 不成立 → 归该系统（dsh / cron）

**独立口规则**：凡是有独有机制、坑只有它自己的人才懂的系统，给它一个**物理子目录**（`tips/dsh/`、`tips/cron/`）——文件在哪个目录就是哪个领域，写路径天然强制，无需每次判断。新增系统 = 建目录 + schema 枚举加一项 + 面板自动出现标签页（按路径前缀推导）。通用池（根目录）吸收其余一切，不细分。

**author 规则**：写"谁写的"（来源轴），与 domain 无关——dsh agent 也会踩通用坑（author=dsh-agent, domain=general）。新 agent 不知道身份 → 写"其他"；稳定后由人把它加进枚举。**禁止自创枚举外的值**（schema 会拒绝）。

**存量默认**：缺 domain → general；缺 author → 其他（存量零迁移，schema 不标红）。

## 四、边界（不写入清单）

- **项目设计文档** — 描述系统怎么设计的 → 放 `design-spec.md`
- **当前状态快照** — 工具数、端口号、运行状态 → 放 `state/`，自动落盘
- **操作历史** — 谁在什么时候做了什么 → 放 `state/call-log.jsonl`
- **调度中心经验** — 属于调度中心的踩坑 → 写入统一库 `tips/cron/`（调度中心服务已指向统一库，cron agent 经其 API 写入即落此目录）；视图只在 3099，3100 不再展示
- **代码逻辑** — 能从代码本身读懂的 → 代码就是真相源
- **CLAUDE.md 已有** — 行为规则、项目约定 → 已在 CLAUDE.md
- **Git 已记录** — commit message 说清楚了的 → git log

## 五、维护

- **过期即归档。** 路径变了、API 变了、不再适用的——移 `tips/archive/`，从检索面移除，保留历史可恢复。淘汰触发：① 根因已被代码修复 ② 与现有 tip 重复 ③ 症状消失
- **发现即修。** 读到一个 tip 发现有错——立刻改，不等下次
- **重复即合并。** 同一个 insight 两个文件——合并为一个，被合并方移 `tips/archive/`
- **不凑数。** 3 条高质量 > 30 条流水账
