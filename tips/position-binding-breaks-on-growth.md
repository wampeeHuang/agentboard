# 位置绑定是"以后一定会错"的绑定

## 现象

信息模板里"每个维度必填/选填"存成数组 `['required','optional']`，读取时配
`dimensions[:2]`。系统一直"正常"——直到两件事发生：

1. **结构长出了第三项**（每领域维度上限由 2 放开为 3）→ 第三个维度**永远取不到必填**，
   而且没有任何报错，用户勾了也不生效。
2. **顺序变了**（领域里调整维度顺序）→ 必填**悄悄绑到另一个维度上**。
   改的是"第几格"，用户以为是"哪个维度"。

## 根因

位置是**结构的属性**，不是**语义的身份**。只要被绑定的东西可增删或可重排，
位置索引就会在某个时刻指向另一个对象，而且**失效是静默的**。

同样的味道：配置里 `dimension_requirements[index]`、`items[0]` 当默认值、
"第一列是主键"这类隐含约定。

## 修复/步骤

- 落盘改成按身份查表：`{领域id: {维度id: 'required'}}`
  （维度 id 只在领域内唯一 → **必须带领域这一层**，不能只写维度 id）。
- 升级旧数据时按**各领域自己的**顺序逐位对应，不要把多个领域的维度拉平成一个序列——
  拉平会把 A 领域的必填记到 B 领域头上。
- 配置里**不存在**的 id 不产生要求，也**不顺位继承**给下一个。
- 前端渲染也按 id 列：有几个真实维度就列几行，不再写死"维度一/维度二"两行。

## 预防

- **可枚举的结构一旦放开上限，必须回头搜所有 `.slice(0, N)` / `[index]`**。
  放开上限是一次语义变更，不只是改个校验数字。
- 改这类结构时补一条**"顺序变了行为不变"**的测试：把维度倒序保存，
  断言必填仍落在同一个维度上。这条测试就是位置绑定的回归锁。
- 沿革留痕：改名不改 id、旧名进 aliases、删项记 `deprecated_*` 并写 op-log，
  这样"这个词什么时候没的、并入了哪个"以后查得到。
