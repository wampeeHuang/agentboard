# 按文件名认进程会跨项目误伤：一次"清僵尸"清掉的是另一个服务

## 现象
灵感图库的调整总表有一条判据「清掉僵尸进程：workbench.py 进程数应为 1」，
它按命令行做 `-match 'workbench\.py'` 计数，长期报「进程数 = 2」，判据一直红。
拿到用户授权后按它去"清理"，杀掉 PID 33212 —— 结果那个进程听的是 **:8770**，
是兄弟项目**字荐**的服务进程（字荐的入口文件也叫 `workbench.py`）。
supervisor 在约 1 秒后拉起了新进程（PID 42284），字荐 HTTP 200 恢复正常，未造成数据影响；
但"按判据行事"这个动作本身是错的：判据把别的项目算成了本项目的垃圾。

## 根因
两个独立的问题叠在一起：

1. **判据用了"名字"，而"名字"在这台机器上不唯一。** 本机有多个自建应用，入口文件
   都叫 `workbench.py`（一类目一应用的架构使然）。用文件名/命令行子串匹配进程，
   匹配集里天然混着别的项目。
2. **进程的"归属"没被验证，只被假设。** 命令行是相对路径（`python workbench.py`），
   本身不含项目信息；唯一可靠的归属证据是**它占着哪个端口**，而这一步当时没做——
   看到"不监听 8771"就下结论"是本应用的僵尸"，实际上它监听的是 8770。

更隐蔽的是：这个判据"红得很有说服力"。它给出一个具体数字（进程数 = 2）和一个具体
行动（清掉多余的），于是很容易照着做——**错误的判据比没有判据更危险，因为它附带行动指令**。

## 修复/步骤
1. 判据改为守**资源不变量**而不是数进程：`@(Get-NetTCPConnection -LocalPort 8771 -State Listen).Count == 1`，
   并把归属 PID 打印出来。
   这才是真正要防的事——Windows 的 `SO_REUSEADDR`（Python `HTTPServer.allow_reuse_address`
   默认开）允许第二个进程抢绑同一端口，那时两个进程各有一把进程内锁，写接口的互斥形同虚设。
2. 杀进程前先问三个问题：**它听哪个端口？那个端口是谁的？杀了谁会受影响？**
3. 修完立刻验证被"顺手影响"的邻居：字荐 `:8770` HTTP 200、本应用 `:8771` 单监听。

## 预防
- 机器上存在同名入口时，**判据一律锚定唯一资源**（端口 / 绝对路径 / 服务注册名 / manifest id），
  不要用文件名或命令行子串。
- 判断进程归属时，命令行只是"线索"，端口与父进程才是"证据"。任务管理器/CIM 给出的是进程列表，
  不是归属关系。
- 看到一条判据输出「数量不对」并附带一个清理动作时，先确认判据自己的作用域——
  跨项目/跨租户工具最容易在这一点上骗人。
- 清理动作完成后必须做一次邻居回归（相邻端口/相邻服务仍健康），因为误伤通常发生在"看起来无关"的服务上。
