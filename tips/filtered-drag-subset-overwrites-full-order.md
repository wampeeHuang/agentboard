# 前端只提交筛选视图里的子集、后端整份覆盖，会把没提交的条目全部挤走

## 现象

面板卡片顺序反复变化，用户反馈“面板怎么又变了”。查排序状态文件，发现它被写成了 **14 条**和 **27 条**两个版本——而 14 和 27 正好等于「开发与工具」和「飞书与办公」两个分类筛选下可见的卡片数量。

也就是说：**被写进排序文件的是完整顺序，还是当前可见的那几张，肉眼看不出来**，但后者会让其余 62 张技能全部跳到末尾。

## 根因

前端拖拽结束后，只把**当前渲染出的卡片 id** 提交给排序接口：

```js
var names = Array.prototype.map.call(grid.querySelectorAll('.tool-card[data-id]'), c => c.getAttribute('data-id'));
persistCapOrder(names);
```

筛选生效时 `grid` 里只有该类别的卡片。后端把它当**完整顺序**整份覆盖落盘。读取时按"索引存在则排前、不存在则排后"处理，于是没出现在文件里的技能全部丢到末尾——表现就是“面板自己重排了”。

前端提交子集本身没错（筛选视图里只能拖到看见的卡），错在接口把子集当全集。

## 修复/步骤

在后端把提交项**按原有槽位插回**，而不是覆盖：

```js
var current = applySkillOrder(all).map(s => s.id || s.name);   // 当前完整顺序
var provided = new Set(clean);
var slots = [];
current.forEach((id, i) => { if (provided.has(id)) slots.push(i); });
var merged = current.slice();
slots.forEach((pos, i) => { merged[pos] = clean[i]; });
writeSkillOrder(merged);
```

性质：提交全集时结果与提交内容完全一致（槽位就是全部位置），提交子集时未提交项原地不动。顺带把排序范围收窄到面板实际展示的技能，避免把插件缓存那 300 多条无关 id 也写进文件。

## 预防

- 任何"提交当前可见/当前选中项"的写入接口，**必须显式区分 merge 与 replace**，并在后端实现槽位合并——"前端保证会提交全集"是不能当契约的，筛选、分页、权限任何一项都能让这个假设失效。
- 排序/优先级这类"全序状态"，落盘前先断言：写入条数 == 预期全集条数，或明确走 merge 路径。
- 验收判据要能抓住这个 bug：**提交 N 条后断言其余条目顺序完全不变**；只验证"拖过的那张动了"会漏掉全部。
- 排查同类问题时，排序文件里的条数本身就是线索——如果它等于某个筛选条件的条目数，基本就是子集覆盖。
