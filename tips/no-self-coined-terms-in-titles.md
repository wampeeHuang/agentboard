# 别给归纳出来的东西起名字：读者看不懂的是你造的词

## 现象

拆解 Descript 时把它的画面侧机制归纳成一篇笔记，起名 **「Descript 的画面层模型」**，首段写「判断一个编辑器能不能扛住复杂片子，看它有没有清楚的作用域单位」。

用户回：「What exactly is the title『Descript's Frame Layer Model』trying to explain? 什么叫画面层模型？我怎么看不懂。」

## 根因

**「画面层模型」这个词是造出来的**——源文档里从头到尾只有两个概念：Scene（场景）和 Layer（图层），没有"画面层模型"这个东西。

造词的成本被低估了：一个读者没见过的词，无法从字面猜出它指什么；而我为了让它"成立"，又在首段加了一层抽象框架（"作用域单位"），结果是**用一个抽象词解释另一个抽象词**，读者从第一句就进不来。

这违反的是知识库自己早就写下的规矩：*「定义必须是来源翻译，不是 Agent 归纳。找不到来源 → 不单独建页。」*

注意与已有 tip `agent-invented-design-constraint.md` 的区别：那条讲**自创设计参数**（宽度、间距），本条讲**自创分类词汇**。前者会做错东西，后者会让对的东西没人看懂。

## 修复

1. **标题换回源文档的实际概念**：「Descript 的画面层模型」→「Descript 的场景与图层」。
2. **首段改成回答"这页帮我决定什么"**，不再讲抽象判断：
   > 想知道"+加个标题""换掉这段画面"这类操作会不会影响到别处，看这一页。
3. **删掉所有自造术语**（"作用域单位"、"画面层模型指…"）。
4. **按读者会问的顺序重排**：两个词分别是什么 → 图层默认活多久 → 切场景的两种后果 → 延展后是同一个对象 → 场景即操作范围 → 粘贴的定位基准 → ……（原来是按我的归纳框架组织的）。

## 预防

- 落笔前问一句：**这个标题里的名词，能在来源里指出对应物吗？** 指不出就是自造的，换成来源的词。
- 归纳**可以做**，但归纳结果要作为**正文里的解释**出现，不要升级成标题与新术语。标题用源词，解释用归纳。
- 首段禁止出现"模型""框架""范式"这类抽象容器词——它们不提供信息，只要求读者先接受一个前提。
- 发现"我加了一层框架才讲得通"时，通常说明**这层框架不该存在**，要么删掉它直接讲机制，要么拆成两页。
