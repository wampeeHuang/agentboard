# 为了迁就渲染参数去改数据形状：加出来的层必然长出废链，还会掩盖真问题

## 现象

把 WikiArt 的分类落成观察用的画布。它的顶层有 **14 个并列的组**（古埃及艺术 / 古希腊艺术 /
西方中世纪艺术 / … / 当代艺术 / 东亚 …），而配色方案只区分得开 **7 支**。

Agent 的做法：**凭空加了一层「时代」**，把 14 个组并成 6 块，再加 1 块题材，凑成根下 7 支。

用户盯着画布问了一句：

> 「现代艺术的分类单流经过现代，再经过流派组。怎么会这么深的一棵树，然后还只有它呢？」

## 根因

**把「表示层的容量」当成了「数据必须满足的形状」。**

颜色是表示层的**一个参数**。它不够用的时候，该改的是那个参数，不是数据。

事后 DOM 实证：源页面是**一个扁平 `<ul>`**，14 个 `li.header` 与 218 个 `li.dottedItem`
**是同一层级的兄弟**（源码缩进 20 vs 24 只是排版）。`header` 靠 CSS 的
`margin-top:25px; font-weight:bold` 做出「小节」的样子，**结构上没有父子关系，
也没有比 header 更高的一层**。「时代」在源数据里**找不到任何对应物**。

## 代价（两层，第二层更贵）

1. **必然长出废链。**「现代」那块底下只挂着 1 个组，于是出现
   `现代 → 流派组 → 现代艺术` 这条**三跳只为托住一个组**的路径。用户一眼就看出来了。
2. **掩盖了更严重的问题。** 做这次「归纳」的时候，注意力全在"怎么并成 7 块"上，
   结果**只列了源站 9 本词典里的 2 本** —— 漏掉的里面正有用户最想要的
   「艺术运动」189 条和「画派与团体」**289 条**。**为了凑一个颜色，丢了一千多条数据。**

## 口径

> **超色板时，改的必须是颜色，不是数据形状。**
> 三选一：① 扩色板 ② 让这一层不着色 ③ 换装箱方式。
> **绝不加层、绝不并项、绝不改名。**

判据：**画布上每一层都必须能在源数据里找到对应标记**（源页面有 `li.header`，才允许有"组"这一层）。
指认不出的层 = 自创层，当场删。

## 与既有条目的关系

`agent-invented-design-constraint.md` 讲的是**自创 UI 规格**（卡片宽度、手机框）。
本条是它的**数据侧对偶**：不是自创规格，而是**为了迁就规格去改数据**。
前者是"多加了一个约束"，后者是"为了满足一个约束而篡改事实"，后者更隐蔽也更贵。
