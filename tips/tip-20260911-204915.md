# 字体子集 woff2 若不声明 unicode-range，浏览器仍会拉完整 TTF 补缺字

## 现象

页面首屏 71.8 MB，其中字体占 41.4 MB（两个未压缩的中文变量字体 `NotoSerifSC-VF.ttf` 24 MB、`NotoSansSC-VF.ttf` 17 MB），而整个界面文本 + 全库图片标题只用到约 1800 个不同字符。

把字体子集化成 woff2（50.5 MB → 1.7 MB，省 96.6%）并让 `@font-face` 优先引用 woff2 后，**浏览器仍然下载了 17 MB 的完整 TTF**，优化几乎没生效。

## 根因

两件事叠加：

1. **浏览器把 woff2 子集当作"该字体族不完整的来源"。** `@font-face` 只有 `src`、没有 `unicode-range` 时，浏览器认为这条 face 应该覆盖它需要渲染的**全部**字符；一旦遇到子集里没有的字形，就会去 `src` 列表的下一项（完整 TTF）取字——于是 17 MB 照样下载。
2. **同一字体族的多条 `@font-face` 是并存关系，不是覆盖关系。** 上游生成的 tokens CSS 自带 8 条指向 TTF 的 `@font-face`，我又加了一层指向 woff2 的声明；即使字重范围完全相同、加载顺序在后，浏览器仍把它们当独立 face 处理，两套文件都被请求。**靠 CSS 权重或加载顺序无法"顶掉"另一份 `@font-face`。**

判据：`document.styleSheets` 里能看到两套规则都在，`performance` 里 woff2 和 TTF 都被请求。

## 修复/步骤

1. 先量化：把字体文件体积和实际下载量列出来，确认瓶颈真是字体而不是图片（本例图片只占 3.1 MB / 120 张）。
2. 子集化的字符集口径取**界面文本 + 全库数据文本**，不要只取界面文本——多语种标题（英/日/韩/俄/土耳其/阿拉伯）会回退系统字体导致字形不一致。本例多纳入约 400 字符只多 0.27 MB。
3. **让字体声明只有一份**：直接改生成源（本例在快照同步脚本里把 `@font-face` 的 `src` 从 `.ttf` 改写成 `.woff2`），而不是叠加一层覆盖 CSS。
4. **不要在 `src` 里保留 TTF 后备**——保留就等于给浏览器留了一条下载 41 MB 的路。子集覆盖不到的罕见字回退系统字体，这个代价远小于 41 MB。
5. 验证要看**实际下载了哪些文件**，不是看 CSS 写了什么：

```js
page.on('response', r => { if (/\.(ttf|woff2)$/.test(r.url)) console.log(r.url,
  r.headers()['content-length']); });
```

## 预防

- 交付 CJK 站点时**先查字体体积**：完整 CJK 字体动辄 15-25 MB，常常是首屏第一大项，比图片更值得先修。
- 子集化后一定要在真实浏览器里确认**没有 TTF 请求**，而不是只看 CSS 的 `src` 顺序。
- 如果确实需要 `unicode-range` 精确控制，注意压缩率可能很差：本例 1262 段 range 展开约 9.7 KB，随 CSS 一起传并不划算。
- 子集是**会过期**的：新录入的生僻字会落回系统字体。要留一个可再生脚本 + 一条"woff2 不早于 TTF"的漂移门禁。
