# 交付前先声明"本会话会动哪些目录"，否则子代理会把搬迁当成丢失

## 现象

派了一个子代理去加工 `raw/文章/descript-拆解/` 下的 28 个文件。它起手 glob 命中 28 个、读完 25 篇，随后 3 篇报 not found，接着连读过的也全部 not found。

它的结论是：**「目录在本次会话进行中被并发进程删掉了，`raw/` 被 gitignore 所以取不回」**，并请求授权"从官方全文快照零改动重建这 28 个文件"。

实际上目录确实消失了——**但不是丢失，是我按摄入管线主动把它迁到了 `raw/已消化/`（加 `descript-` 前缀）**。文件一个没少。

值得肯定的是它做对了三件事：没有重建、没有凭记忆伪造内容、明确报告"我判断为不可恢复"。所以损失为零，只是白跑一轮 + 一次需要澄清的告警。

## 根因

派任务时我只写了"不要修改目标目录之外的文件"，**没有声明我自己会并发修改这个目录**。子代理对文件系统的观察是它唯一的事实来源，观察到"文件在本次会话中消失"时，推断为丢失是完全合理的。

同时它的失败模式也确实被现有环境放大了：`raw/` 在 `.gitignore` 里，所以它一查 git 就得出"没有恢复点"，进一步坐实了"丢失"的结论。

## 修复/步骤

- 向该子代理补发澄清（说明搬迁脚本名、目标命名规则、新路径），并给它新的 glob 目标让它继续。
- 后续同类任务改成：**开工前把"已知的并发改动"写进任务书**。

## 预防

派子代理前，任务书里加一节「环境与并发」，至少写清：

1. **本会话会动哪些目录**：例如"我可能在你作业期间把 `raw/文章/X/` 迁到 `raw/已消化/`，文件名加前缀 `X-`"。
2. **发现文件消失时的判断顺序**：先查是否被移动到同盘邻近目录、查 `_runtime/` 里的搬迁脚本日志，**再**下"丢失"结论；找不到就报告，不要重建。
3. **明确禁止自我修复**：写死"不要重建目录、不要凭记忆补内容，发现异常先停下来报告"（本例子代理自发做到了，值得写成硬规则）。
4. **告诉它不可恢复性的边界**：本例 `raw/` 无 git 历史是事实，所以"谨慎"是对的，但结论要由搬迁记录而不是 git 决定。

反向的坑同样存在（见 `git-deleted-not-corruption-ask-intent.md`：把用户有意的删除当成损坏去 restore）。两者合起来是一条：**文件消失时先归因，再动作；归因的依据是并发记录，不是自己的观察窗口。**
