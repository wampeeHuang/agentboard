# 以 ID 为键的状态文件不能按名字批量写：同名条目会互相顶掉

## 现象

面板显示名重名时会出现"改了没用"的假象：某技能在面板上仍是英文用途，但状态文件里明明有一条同名记录已经写好了中文。查下去发现——**写好的那条是它的同名孪生**，目标那条根本没被碰到。

本机实例：`skill-creator` 同时存在于统一库和平台内置两处，是两条独立记录（同显示名、不同来源路径）。按名字批量写时，后出现的那条覆盖了前一条的映射，值就落到了孪生身上。

## 根因

状态文件以**来源 ID**（真实路径的哈希）为键，同名是两条独立记录；批量脚本常用"人可读名 → id"建索引：

```js
const byId = new Map();
for (const s of rows) byId.set(s.name, s.id);   // 同名后者覆盖前者
```

`Map.set` 对重复键是覆盖，不报错、不提示。于是"11 条都写成功"的日志是真的，只是其中一条写给了另一个对象。

## 修复/步骤

1. 定位：把同名条目全列出来（`id` + 归属/来源），确认到底有几条：
   ```js
   const rows = caps.skills.filter(s => s.name === 'skill-creator');
   // → 99be6027(已入统一库, managed=true)  ab3a2134(平台内置, managed=false)
   ```
2. 按 ID 精确写入，不经过名字：
   ```js
   const target = rows.find(r => r.managed);      // 用可区分的属性选目标，而不是"第一个/最后一个"
   registry[target.id].summary = SUMMARY;
   ```
3. 回读两条记录，断言**只有目标条目变化**——只回读一条无法发现写错对象。

## 预防

- 凡是状态以 ID 为键，任何按人可读名做的批量操作，**第一步先做重名检测**：同名计数 > 1 就停下来人工确认。
- 面板显示名、"名"字段是**展示属性**，不能当主键；批量脚本里出现 `set(name, id)` 这类映射时要默认它是可疑的。
- 批处理写完必须做双向核对：目标条目变了 **且** 同名孪生没变（只查前者会漏）。
- 宁可让显示名重名（人看得懂），也不要把重名压成一条——合并会丢来源，写错却看不出来。
