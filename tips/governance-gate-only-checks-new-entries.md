# 预检门禁只判"新建"的一级条目：存量违规目录永远不会被发现

## 现象
`workspace-governor` 的 PreToolUse 预检把 `_knowledge_base` 列在 BLOCK 名单里（反射性命名的根目录），
但实测：对**不存在**的 `outputs/` 判 BLOCK，对**已存在**的 `_knowledge_base/` 判 ALLOW。
结果是这个目录在门禁眼皮底下活了很久，直到一次主动审计才被发现——而且它已经混装了三类东西：
研究笔记（该进 `docs/research/`）、审计产物（该进归档）、被取代的旧稿（该进归档）。

## 根因
门禁的判断入口是 `new_top_level = bool(parts) and not first_entry.exists()`——**只对"这次新建的一级条目"做范式检查**。
这个设计对"防新增"有效，对"清存量"完全无效：目录一旦先于门禁存在（或被门禁之外的手段造出来），
它就永久免疫。预检门禁回答的是"你这一步是否制造了新的结构违规"，不是"这个工作区是否合规"——
两件事被混为一谈，于是"门禁全绿"被误读成"结构干净"。

## 修复/步骤
1. 别把预检门禁当合规审计。合规结论只能来自**标准槽位清单与磁盘实际一级条目的差集**：全量枚举一级条目 → 逐个归类为标准槽位 / 允许例外 / 违规
2. 对违规项按"零风险优先"分批迁移，每批可逆、逐批验证（本次：文档→`docs/research/`、不可再生证据→`archive/`、旧稿→`archive/`）
3. 迁移后立刻做一次反向核对：全树 grep 旧路径，改掉所有失效引用（本次改掉 8 处，含两个 `themes/` 下的 HTML）
4. 把"判据"写进项目 CLAUDE.md，别只写结论——否则下一轮又会造出同类目录

## 预防
- 审计脚本的两个判据要分开：**增量判据**（本次改动是否新增违规）与**存量判据**（当前结构是否合规）。只有后者能得出"干净"的结论
- 门禁白名单/黑名单的每一条，都配一个"存量扫描"用法，否则名单只防未来不治现在
- 看到"门禁通过"先问一句：这条门禁判的是增量还是存量？增量绿灯不构成结构合规的证据
- 这类"命名即范式"的黑名单（`output` / `generated` / `tmp` / `_knowledge_base`）要定期拿磁盘实际一级目录去比对，而不是拿它去比对新建请求
