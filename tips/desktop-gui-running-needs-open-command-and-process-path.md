# 无端口桌面 GUI 的“运行中”不能只依赖 PID 账本，启动与再次打开也必须拆开

## 现象

无端口桌面 GUI 从工具架启动后能显示“运行中”，但卡片在运行态只剩状态文字，没有“打开”按钮；控制平面重启后，应用窗口明明还在，卡片又可能变成“未运行”。如果直接复用启动接口作为“打开”，它会被防重复启动的 PID 检查拒绝，或产生第二个实例。

## 根因

这类工具同时混淆了两组不同职责：一是把 `startCommand` 同时当成首次启动和运行中唤回；二是把控制平面写下的临时 PID 账本当成桌面应用本身的持久运行证据。PID 账本只能证明“本轮由我启动的包装进程还活着”，控制平面重启或启动包装器退出后就会失效；而 `pythonw.exe`、`node.exe` 等共享运行时仅按进程名检测又会误报其他工具。

## 修复

在 manifest 中显式分离三个合同：`startCommand` 负责首次启动，`openCommand` 负责运行中唤回窗口且不改写 PID，`processPath` 用完整可执行路径确认真实 GUI 进程。前端只有在 `state=running` 且声明了 `openCommand` 时才显示“打开”；后端提供独立 open 动作，不经过 start 的防重复启动路径。唤回脚本先查真实应用进程，调用窗口恢复/前置 API 后立即退出；不存在进程时仍走正常启动并等待真实 GUI。

## 预防

注册无端口桌面 GUI 时，不要只填写 `type: cli` 和 `startCommand`。先回答三件事：如何准确识别真实进程、已运行时如何唤回、重复点击是否保持单实例。共享运行时必须填写完整 `processPath`，不要退化为 `pythonw.exe`/`node.exe` 进程名。验收至少覆盖：首次启动、运行中按钮可见、点击打开后 PID 不变、控制平面重启后仍判定运行、窗口退出后状态恢复停止。
