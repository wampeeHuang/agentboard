# 参考架构源头声明规则

type: writing-rule
date: 2026-08-11
source: Agent 项目文件架构知识库——外部审查发现多处原型声明过度

## 现象

参考架构文档中写"原型来自 X"，读者（和后续 Agent）会默认 X 为整棵目录树背书。审查时发现：Airflow、GitHub Actions、Google ADK 等来源支持的是**概念分离**（定义/实例分离、制品/缓存分离），不推荐文档中展示的具体目录结构。

## 根因

写作时为了增加可信度，容易把"概念来源"的声明扩大到"整棵目录树来自 X"。概念来源和实现落地是两层——不加区分会制造虚假权威感，被懂行的人揪出来伤公信力。

## 修复

必须区分两句：

| 可以说 | 不能说 |
|--------|--------|
| "定义与运行实例分离——来自 Airflow DAG/DagRun 概念" | "这棵目录树是 Airflow 的原型" |
| "制品与缓存分开管理——参考 GitHub Actions artifacts/cache" | "GitHub Actions 使用这套文件夹结构" |

具体做法：文档顶部加总声明"目录树是本文基于概念的落地方式，非上游项目的实际目录"。对来源最弱的条目（如事件驱动），在原型行直接标注"原型支持的是概念，目录结构是本文示例"。

## 预防

写完参考架构后，逐条原型声明问一个测试问题：**"X 的官方文档里能找到这棵目录树吗？"**

- 能 → 写"原型树来自 X"
- 不能，但概念来自 X → 写"概念分离来自 X，这棵树是本文的落地方式"
- 概念也没有对应 → 标"示例，非来源原型"
