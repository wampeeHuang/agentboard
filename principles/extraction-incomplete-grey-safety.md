# 数据源提取不完全时，策展数据绝不因源缺失自动消失——变灰 + 人工删

## 是什么

当系统从外部数据源（二进制、API、目录树、远端清单）提取数据，并在其上叠加人工策展（标注、分类、中文名、说明）时，提取可能永远不完整——源里没有 ≠ 数据不存在，可能是解析漏了、字段形态变了、或源本身就缺。此时若策展数据因"源里找不到"自动消失，等于把机器提取的盲区变成人工策展的不可逆删除。

规则：**源缺失 ≠ 删除信号，是灰显信号。** 提取不到的对象变灰（保留、可读、可操作），只有人工显式删除才消失。

## 怎么用

1. **识别提取层的不确定性**：凡是 best-effort 提取（宽松正则、启发式、带上下文窗口的解析），先假设它可能漏——不是假设它完整。
2. **三段式合并视图**：源与策展按状态合并——已策展（源命中）→ 未策展 → 源缺失（灰排末尾）。缺源不代表不存在，单独成段展示。
3. **默认灰不删**：策展数据源缺失时默认变灰保留。删除是唯一消失路径，且必须是人工主动触发。
4. **给灰显一个解释**：灰段要有"为什么灰"的可读线索（如删除线 + 弱化色），用户知道这是"源没检出"，不是 bug。

## 案例

agentboard 命令 tab：从 claude.exe（242MB JS bundle）宽松正则提取斜杠命令，抓 90 条，seed 全量 106 行。cost/remember/worktree/doctor 等命令真不在二进制里——永远扫不到，不是正则不够宽。若按"源里没有就自动删"同步，这 16 条策展标注会被静默抹掉。

**用之前**：直觉是"源里没有 = 删掉同步干净" → 提取漏一条，策展删一条，越同步越丢。
**用之后**：源缺失的命令变灰沉底 + 删除线，保留可再标注，用户显式删除才消失 → 提取盲区可见、策展零误删。

## 边界

- 仅当提取层确实 best-effort / 不完整时才灰显。源是权威全集且确定性读取（如自己的 SQLite 表），"源没有 = 真没有"成立，正常删。
- 灰 ≠ 不可操作。灰对象仍应可编辑、可删除、可恢复标注——灰只是状态提示，不是权限降级。
- 灰名单本身不落盘为永久隐藏名单——那是另一种不可见副作用（见 `annotation-requires-edit-delete-reverts.md`）。灰是渲染态，来自合并计算，不持久化。
