# 制度必须有执行验证：巡检/门禁覆盖什么边界，就查什么风险

type: governance
date: 2026-08-25
source: agentboard 对抗性审查——L3 运行治理声明 vs 执行断层（_runtime 892 文件失控无人察觉）

## 是什么

治理制度声称守护的边界，必须有对应的确定性检查把它兜住。**制度只覆盖"查得到的风险"，没执行的制度是纸面声明。**

## 怎么用

### 审查一个治理声明时查三层

1. **声明了什么**：文档/注册表声称覆盖哪些风险（巡检、门禁、schema 校验……）
2. **执行了什么**：实际跑起来查什么（检查项定义、hook、脚本）
3. **断层在哪**：声明的边界 ⊄ 执行的边界 → 未覆盖区域必然失控

### 判据

- 巡检注册表检查工具架功能状态（端口/健康/冲突）→ 它就只能兜住功能风险，兜不住仓库卫生
- 门禁拦截一级目录结构变更 → 它管不到运行产物目录内的堆积
- schema 校验 manifest 字段 → 它校验不了"该 ignore 的没 ignore"

### 关键追问

```
问: "我们有巡检，为什么 _runtime 会失控到 892 个文件没人发现？"
答: 因为巡检查的是工具架卡片，不是仓库卫生。制度声明了 L3 治理，但 L3 的"自动审计与恢复"只覆盖了功能面，没覆盖存储/文件面。声明 ≠ 执行。
```

## 案例

**agentboard _runtime 失控**：项目自称 L3 运行治理（宪法 + 巡检注册表 + 门禁），但运行产物目录堆积 892 文件 / 26MB 一直无人察觉，直到一次性对抗性审查才发现。巡检检查项全在工具架功能面；git 未跟踪噪音 4 组、_runtime 堆积、隐私 profile 泄漏全在盲区。

**不用这个原则之前**：以为"有巡检 = 卫生有人管"。
**用了之后**：审查治理声明先问"这条风险谁在查"，查不到 = 补检查项或承认盲区，不让声明和现实脱节。

## 边界

- 不是所有风险都要自动化兜——一次性风险人工核对即可；反复出现的风险才需要固化成检查
- 补检查项的前提是有确定性消费者（脚本/巡检/门禁），没有就只标注盲区，不制造无读者的检查文件
