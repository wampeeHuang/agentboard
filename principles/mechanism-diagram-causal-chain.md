# 机制图画因果链，不画组件堆：主宾 + 常态 + 异常 + 交汇点

## 是什么

机制/架构图被"读不懂"，八成不是读者笨，是图只画了组件堆叠，没画机制本身。机制 = 谁主动（主宾）、常态怎么走、挂了走哪（异常分支）、多层之间交汇点在哪。一张合格机制图，读者应该能复述完整因果链，而不是反过来问"这是谁触发谁？"

## 怎么用

画机制图/写机制说明，验收四问：

1. **主宾明确**：每个箭头的动词方向，谁主动谁被动？"定时轮巡去看守卫"就是主宾反了——实际是任务计划叫醒守卫、守卫上门探活 supervisor。动词方向说反 = 机制讲错，读者一眼能识破。
2. **常态路径完整**：平时一条路从头走到尾，每个"谁找谁"都要有箭头和标签，不能只有组件名。
3. **异常分支画出来**：挂了怎么办？连挂几次怎么办？只画 happy path 的机制图是自嗨——异常分支才是机制设计的核心，也是读者最想确认的。
4. **交汇点标注**：多层系统里哪个组件是两层之间的结合点，明说。读者才不会把各层当平铺的平级组件。

## 案例

supervisor 全景图初稿是三层套娃（supervisor/guard/registry 平铺），用户问"是开机自启也触发外部守卫吗？定时轮巡也触发吗？"——图没回答，因为图里根本没有守卫与 supervisor 之间的因果箭头。重画后：绿层=进程层（启动+看护）、强调色层=服务层（自愈），supervisor 是交汇点；画了三条真实路径——开机注册表直接拉起 / 任务计划每 5 分钟叫醒守卫 / 守卫探活挂了重启、连挂退避。用户读完能复述机制，不再问触发关系。

**用之前**：组件堆叠图，用户连问三次触发关系。
**用之后**：因果链图，用户一眼看出谁主动谁被动。

## 边界

- 适用于机制/架构说明。流程图、数据流图已有自己的约定，不强行套"交汇点"。
- 图越复杂越要画因果链。简单静态结构（目录树）不需要——那是目录不是机制。
- 判断标准是"读者能否复述因果"，不是图是否美观。审图让读者试讲一遍，讲不出来 = 图没达标。
