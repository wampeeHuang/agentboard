# 第一性原理审查：拆到原子，逐条验证假设

type: review
date: 2026-08-01
source: 版式画廊 v5 产品定位审查

## 是什么

把方案拆到不可再拆的原子事实，逐条追问"这个假设一定成立吗？"。保留原子事实，丢弃推导假设，从原子事实重新推导方案。

## 怎么用

### 四步检查清单

1. **列假设**：把方案背后的每个隐含假设写出来。不只写"我们的方案是X"，要写"方案X成立的前提是A、B、C"
2. **逐条拆**：每个假设追问——"这一定成立吗？有没有反例？"
3. **区分类别**：标记每条为 原子事实（不可再拆）或 推导假设（可以再拆）
4. **重推导**：只从原子事实出发，重新推导方案。看看和原方案差多少

### 关键追问

```
假设: "AI 需要设计 token 来生成好 UI"
拆: AI 真的需要 token 吗？需要的是约束还是数据？
再拆: token = 约束的载体。AI 需要的是"设计约束"，不是"token 数据"
结论: 项目的核心价值是"编码设计决策"，不是"收集 token 数值"
```

## 案例

**版式画廊 token 价值审查**：

| 层 | 原有假设 | 拆穿 |
|---|---------|------|
| Token 是设计约束 | 真的。CSS 变量确实能约束 AI 输出 | ✅ 成立 |
| 真实网站 → 好 token | 未必。设计师用 `--c-fg` 不叫 `--color-text`，变量名乱不影响网站好看 | ❌ 弱假设 |
| Token 库 = AI 能用了 | 不够。Agent 拿到 hex 值有用，但"这个颜色用在哪"比"颜色是什么"更重要 | ❌ 缺使用语境 |
| 数量 = 价值 | 不是。1000 个低质量 token 集 < 10 个审计过的完整 token 体系 | ❌ 规模不产生价值 |

**推导出缺失的一层**：设计决策层（Design Decision Layer）——不只给 token 值，还告诉 Agent 怎么用。

## 边界

- 不适用于已经过大量实践验证的成熟方案（如"用 HTTPS 不用 HTTP"——不需要拆）
- 假设数量 < 3 的方案可能不值得用第一性原理——太简单，直觉就够了
- 拆穿假设后需要重建方案，不能只拆不建
