# 一类目一应用 + 只读薄聚合，不做大而全

## 是什么

面对「图片、音频、字体、提示词、文件」这类互斥且交互差异大的资产类型，优先把它们拆成各自独立的单品类应用（自有 UI、自有数据真相源、自有皮肤），用一个只读的薄聚合层（入口/健康/全局搜索索引）把它们串起来，而不是继续往一个「什么都能收」的大应用里加类型。文件系统/本地文件为真相源时拆分成本低——每个应用指向自己的目录即可，无需搬数据。

## 怎么用

1. 判断触发拆分的信号：类型间的画板/标签语义开始互相污染、同类型需要的交互（瀑布墙 vs 试听 vs 字体预览 vs 文本卡）无法共用一套 UI、风险要隔离。
2. 拆分决策先落文档（ADR：现状/共识/决策/边界/阶段），再画执行步骤图，再动手。
3. 每个新应用复用成熟模板（已有一个单品类应用就抄它），不重复造基础设施；皮肤允许各有性格。
4. 聚合层只做登记/启停/健康与（可选）只读全局索引，不拥有也不复制各应用的数据。
5. 先散后聚渐进：先给现有应用做「类型一级粗分/减法」验证，再逐步拆出独立应用，最后挂聚合层。

## 案例

灵感墙从「图片+视频+提示词+链接+文件」的全类型墙收敛为只放图片的「灵感图库」；字荐已是独立的字体单品类应用；BGM/音效「声库」、提示词库按同一模板后建；工具架（Agentboard）就是现成的薄聚合层，每个工具独立 URL 与真相源、各自登记。

## 边界

- 类型间需要高频跨类关联（一张参考图 + 它的 prompt + 配乐构成一个项目单元）时，不要一开始就拆散——先设计薄层的「项目/镜头」只读关联视图。
- 若聚合层开始承担搜索/标签/词表的统一复制，说明拆分越界，应回收到共享词表或合并。
- 数据真相源不能独立、或另无属主的素材，先迁移/备份再拆，别让素材掉进无主目录。
