# 一源多端：数据一个家，所有视图都是读出来的

## 是什么

同一份数据源，派生出多个消费端。不为了展示端建新数据源，不为了"方便展示"做数据拷贝。

一源多端 ≠ 只有一个文件。多源多端 = 多份拷贝各自维护 → 必定漂移。
一源多端 = 一份真相 + N 个读法 → 漂移由架构消灭。

## 怎么用

### 三步检查清单

1. **找真相源**：这个数据"出生地"在哪？谁在写？谁在读？
2. **识别拷贝**：有没有两个文件存了同一份数据？有没有 API 返回了和文件不同的内容？
3. **统一读写路径**：所有写 → 一个入口。所有读 → 从这个入口派生，不是从副本。

### 关键追问

```
问: "我为展示端新加一个 JSON 字段方便渲染——这算打破一源多端吗？"
答: 要看是不是为展示端定制了数据结构。加字段可以，但字段值必须来自真相源，不能"为了展示好看"制造假值。
```

## 案例

**版式画廊的"一源双端"**：

| 层 | 是不是一源多端？ | 实际 |
|---|---------------|------|
| 展示层 | tokens.json → 品牌套件 + AI 范例 | ✅ 一源双端 |
| 产品层 | Token 库 → MCP + REST API + DTCG | ✅ 一源多端 |
| 跨层 | registry.json = 唯一索引 | ✅ 所有查询从 registry 读 |

**之前的误区**：把"一源双端"当成整个产品的架构原则。实际上是展示层的策略。产品有三层：库（内容）→ 接口（分发）→ 展示（端）。每一层都有自己的"源"和"端"，层层派生。

**不用这个原则之前**：把"一源双端"写进了 v4 白板的产品架构——把展示层的策略当成了产品层的架构。
**用了之后**：v5 白板区分了三层，每层是一个明确的一源多端关系。

**跨服务组件共享（tips 面板两站同构）**：

| 层 | 是不是一源多端？ | 实际 |
|---|---------------|------|
| 源 | `~/.agentboard/web/shared/tips-panel.js` | 一份字节，唯一真相源 |
| 端 | 调度中心 :3100 + 工具架 :3099 各自 `/shared/` 静态直读 | ✅ 两站读同一份文件字节，不复制不同步 |

要点：源是**组件字节**不是数据；两个独立服务器各自 `express.static()` 直读同一文件，每站只内联一份纯数据配置（API 路径/文案），组件代码两站完全相同；跨站差异（API 返回形状、文件名契约）吸收进组件内防御函数，不分站 fork。验证同一性用两站拉取字节 **md5 一致**，不靠肉眼。用户否决了所有"同步/守护"方案——源到端单向直读时漂移在结构上不可能，根本不需要同步。

## 边界

- 不要求只有"一个数据源"——不同层可以有不同的源（registry.json、tokens.json、design-decision.json），但每层的源到端关系必须单向
- 缓存可以，但必须声明自己是缓存——标注数据时刻和派生来源
- 要区分"技术实现的一源多端"和"产品定位的一源多端"——前者是架构，后者是卖点
