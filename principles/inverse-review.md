# 逆向审查：什么情况下会失败？倒过来找盲区

## 是什么

不从"怎么成功"想，从"怎么失败"想。列出所有可能导致项目死亡的场景，逐个检查现有方案是否覆盖。

正向思维：怎么做才能成功？→ 容易漏掉失败模式。
逆向思维：什么会导致失败？→ 每条都是一个检查点。

## 怎么用

### 三步检查清单

1. **列死亡场景**："这个项目会在什么情况下死掉？"。不设限——技术、法律、运营、用户行为，全都列
2. **排严重程度**：哪个最可能发生？哪个发生后最难救？
3. **对每条问"现在防了吗"**：防了 → 防线够不够？没防 → 需要加什么？

### 关键追问

```
失败场景: Token 质量不可信 → 用户用一次发现不好用 → 再也不回来
现在防了吗？投票机制防了（好的推上来），但不够。
缺什么？缺"质量门禁"——token 集进入策展层前必须通过自动化审计。
```

## 案例

**版式画廊的逆向审查**：

| 失败场景 | 可能性 | 现有防线 | 缺口 |
|---------|--------|---------|------|
| Token 质量不可信 | 高 | 投票机制 | 缺自动化质量门禁 |
| Agent 拿到 token 但不知道怎么用 | 高 | `/brand/:slug` 品牌套件 | 缺 design-decision.json（使用语境层） |
| 维护成本 > 生长速度 → 库变垃圾场 | 中 | 生长 Agent 自动萃取 | 缺社区策展分流机制 |
| 竞品抄走数据 | 中 | 数据本身不受版权保护 | 护城河不在数据，在策展+语境+验证 |
| 法律风险（Trade Dress） | 低 | 五措施降风险 | 执行需持续监控 |

**发现两个缺口**：使用语境层（design-decision.json）+ 社区策展分流。

## 边界

- 不能只列不防。每条失败场景必须对应一个行动项或确认"风险可接受"
- 低概率高影响的场景也要列——但不能因此让方案变臃肿。"可能被小行星砸"不需要防线
- 和对抗性审查的区别：对抗性 = 竞品怎么杀你，逆向 = 项目自己怎么死的
