# 删功能先画回滚线：减法只收敛可见性，不动真相源数据

## 是什么

当产品收敛或拆分要把某些「类型/能力」请出应用时，删除应作用在**视图与采集边界**上，而不是删除或迁移用户数据；并且改动前先建立可整体回退的快照防线（git tag/分支），把「删代码」从高风险不可逆操作降级为可逐层回退的常规改动。

## 怎么用

1. 先盘点代码里该类型的所有耦合点（后端 scan/采集、前端卡片/详情/筛选/文案），产出边界清单给用户过目。
2. 决策先落 ADR，配执行步骤图；随后打 git tag（如 `pre-xxx-cut`）作为回退线。
3. 后端减法用「过滤 + 收口」而非删数据：列表只回保留的类型；不再支持的采集入口明确报错、落盘的误收素材软删到回收站而非真删。
4. 前端删对应 UI（卡片变体、筛选维度、详情字段、采集表单），保留类型的新语义只增不减。
5. 每步独立 commit（可逐层回退），每步跑语法与端到端回归；收尾同步全部口径（README/宪法/工具架 manifest/.project）。

## 案例

灵感图库从「图片/视频/提示词/链接/文章」收敛为只放图片：`/api/items` 只回 `type=image`，文件采集仅收图片、无图 URL 明确报错，前端载体筛选/非图卡片/文章提炼字段全部退场；磁盘上 2 个链接与 1 篇文章素材数据原地保留，等未来对应单品类库接管扫描。改动前打 tag `pre-image-wall-cut`，任意一步出错可整体回退。

## 边界

- 这条原则针对「让素材在某个应用里不可见/不可收」的减法；真正删除用户数据（清理/回收站清空）必须另走显式确认与备份流程，不适用本原则。
- 数据无第二属主且新属主未定前，别删也别迁，优先原地保留并在宪法/README 里声明等待接管的清单。
